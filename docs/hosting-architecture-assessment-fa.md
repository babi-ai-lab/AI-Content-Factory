# ارزیابی معماری میزبانی و نقشه ارتقای AI Content Factory

**وضعیت:** ارزیابی اولیه، فقط مستندات؛ بدون تغییر در برنامه زنده یا دیتابیس  
**مبنای بررسی:** شاخه `main` در commit `763986e8ade75bd0202852c2f74bcfc1cd6fbde3` (2026-11-08)

## 1. جمع‌بندی اجرایی

پروژه یک وب‌اپلیکیشن Next.js 16 / React 19 / TypeScript است و صرفاً مجموعه‌ای از فایل‌های HTML/CSS/JS نیست. برنامه از API Route Handlerهای سمت سرور، Node.js runtime، رمزنگاری Node، احراز هویت Supabase و پردازش‌های سمت سرور برای تولید محتوا و رسانه استفاده می‌کند.

در cPanel فعلی کاربر گزینه `Setup Node.js App` وجود ندارد. بنابراین استقرار مستقیم نسخه فعلی Next.js روی این هاست، تا زمانی که پارس‌پک پشتیبانی Node.js را برای همین سرویس تأیید نکند، مسیر قابل اتکایی نیست. آپلود خروجی `.next` یا اجرای Static Export به‌تنهایی جایگزین APIهای سرور نمی‌شود.

## 2. شواهد فنی از مخزن

- `package.json`: Next.js 16.4.5، React 19.3.1 و Supabase JS؛ دستورات build/start متکی به Next هستند.
- `.node-version`: نسخه Node برابر 24.22.1.
- `app/layout.tsx`: رندر پویا با `force-dynamic`.
- `next.config.mjs`: تنظیم `assetPrefix` به دامنه Render فعلی اشاره می‌کند؛ برای هر مقصد میزبانی جدید باید بازطراحی شود.
- API Route Handlerهای موجود:
  - `/api/generate`
  - `/api/media/generate`
  - `/api/account/export`
  - مسیرهای اتصال، callback، قطع اتصال، انتشار، وضعیت و زمان‌بندی Instagram
  - `/api/health`
- بعضی مسیرها از Node runtime و `node:crypto` استفاده می‌کنند؛ این مسیرها در هاست PHP-only بدون جایگزینی قابل اجرا نیستند.
- PWA و TWA اندروید به مسیرهای ثابت، manifest، asset links و origin پایدار وابسته‌اند؛ تغییر origin باید با احتیاط و تست جداگانه انجام شود.

## 3. داده و زیرساخت

- پروژه Supabase با وضعیت ACTIVE_HEALTHY شناسایی شد.
- دیتابیس PostgreSQL 17 است.
- جدول‌های public بررسی‌شده RLS فعال دارند.
- تاریخچه migrationها موجود است؛ تغییر schema در این مرحله انجام نشده است.
- Supabase Storage و Edge Functions بخشی از معماری فعلی هستند.
- داده‌های موجود، کاربران، کلیدها، فایل‌های رسانه و تنظیمات احراز هویت نباید در مهاجرت حذف یا بازنشانی شوند.

### هشدارهای خواندنی فعلی Supabase

- Security Advisor: افزونه pg_net در schema عمومی قرار دارد (هشدار، نه مجوز تغییر فوری).
- Security Advisor: محافظت در برابر رمزهای افشاشده غیرفعال است.
- Performance Advisor چند index استفاده‌نشده را گزارش می‌کند؛ با توجه به تازه‌بودن پروژه و حجم پایین داده، حذف آن‌ها در این مرحله توصیه نمی‌شود.

هیچ‌یک از هشدارها در این ارزیابی تغییر داده نشده‌اند.

## 4. گزینه‌های میزبانی

### گزینه A — حفظ Next.js روی محیط Node.js

- کمترین بازنویسی و کمترین ریسک سازگاری.
- مناسب Render یا VPS دارای Node.js 24.
- اگر هدف فقط انتقال از Render به پارس‌پک است، VPS دارای Node.js ساده‌ترین مسیر برای حفظ معماری فعلی است.
- cPanel اشتراکی فعلی تا زمان تأیید رسمی Node.js مناسب فرض نمی‌شود.

### گزینه B — بازنویسی برای cPanel اشتراکی PHP

این گزینه ممکن است، اما تبدیل یک‌به‌یک زبان TypeScript به PHP کافی نیست. لازم است:
- رابط کاربری از وابستگی به SSR و APIهای داخلی Next جدا شود؛
- frontend به خروجی استاتیک قابل میزبانی در Apache تبدیل شود؛
- endpointهای سرور بازنویسی شوند (مثلاً Laravel یا PHP API ساختاریافته)؛
- احراز هویت با JWTهای Supabase و کنترل مالکیت داده‌ها/RLS دوباره طراحی و تست شود؛
- تولید متن، تصویر، خروجی حساب، OAuth و زمان‌بندی با معادل‌های امن PHP/Edge Function جایگزین شوند؛
- assetPrefix، callback URLها، CORS، PWA و Android TWA بازبینی شوند.

مزیت: میزبانی فایل‌های frontend و APIهای PHP در cPanel ممکن می‌شود.  
هزینه/ریسک: بازنویسی قابل‌توجه، تست مجدد همه مسیرها و احتمالاً محدودیت منابع/زمان اجرای هاست اشتراکی.

### گزینه C — frontend استاتیک روی cPanel و backend در Supabase Edge Functions

- می‌تواند نیاز به Node.js در هاست را حذف کند.
- بخشی از APIهای فعلی باید به Edge Functions منتقل یا بازطراحی شوند.
- همچنان نیازمند بررسی سازگاری صفحات Next با Static Export و بازنویسی/انتقال endpointها است.
- از نظر هزینه عملیاتی می‌تواند مناسب باشد، اما backend کاملاً روی پارس‌پک نخواهد بود.

## 5. پیشنهاد مرحله‌ای

1. **تکمیل ممیزی بدون تغییر:** فهرست دقیق routeها، وابستگی‌های SSR، APIها، secrets، cronها، storage و تست‌های موجود.
2. **تأیید امکانات هاست:** نسخه PHP، Composer، SSH/Terminal، Cron Jobs، محدودیت CPU/RAM/زمان اجرا و امکان اجرای Laravel.
3. **تصمیم معماری:** مقایسه نهایی B و C با توجه به امکانات واقعی سرویس cPanel؛ اگر بازنویسی PHP هزینه/ریسک بالایی داشت، VPS Node را به‌عنوان گزینه جایگزین شفاف نگه داریم.
4. **نمونه اولیه جداگانه:** فقط یک مسیر غیرحساس را روی branch/محیط staging پیاده‌سازی و تست کنیم.
5. **مهاجرت تدریجی:** حفظ Supabase و کاربران فعلی؛ انتقال endpointها به‌صورت مرحله‌ای، نه بازنویسی یک‌باره.
6. **آزمون پذیرش:** auth، RLS، تاریخچه، تولید محتوا، تولید تصویر، کتابخانه رسانه، export، PWA، Android TWA، امنیت و عملکرد.
7. **انتشار:** فقط پس از تأیید کامل staging و آماده بودن rollback.

## 6. خطوط قرمز ایمنی

- هیچ تغییری روی `main` یا سرویس زنده صرفاً برای آزمایش انجام نشود.
- هیچ دیتابیس، کاربر، فایل Storage یا secret پاک/بازنشانی نشود.
- کلیدهای API، service_role، رمز cPanel و keystore در Git یا چت قرار نگیرند.
- تغییرات دیتابیس فقط با migration بازبینی‌شده، backup و تست مجاز است.
- PRها ابتدا در branch جداگانه و با تست CI ارائه شوند.
- استقرار نهایی و تغییر DNS نیازمند تأیید کاربر است.

## 7. مورد نیاز از سرویس میزبانی

برای تصمیم نهایی cPanel لازم است مشخص شود:
- نسخه‌های PHP قابل انتخاب (ترجیحاً PHP 8.2/8.3)
- امکان Composer و Terminal/SSH
- فعال بودن Cron Jobs
- دسترسی به document root زیردامنه `app.eltbabak.ir`
- محدودیت حافظه، CPU، تعداد پردازش، زمان اجرای PHP و حجم آپلود
- پشتیبانی از افزونه‌های PHP مانند curl، mbstring، openssl، json، fileinfo و zip

**نتیجه:** بازنویسی برای cPanel امکان‌پذیر است، اما هنوز نباید زبان یا چارچوب نهایی را قطعی کرد. تصمیم صحیح پس از تکمیل ممیزی routeها و مشخصات واقعی هاست گرفته می‌شود. تا آن زمان Render و Supabase فعلی باید فعال و بدون تغییر باقی بمانند.
